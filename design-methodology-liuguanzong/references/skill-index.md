# 产品设计技能总索引

> **这是 12 个设计技能的入口页。** 当你面对一个产品设计任务、不知道从哪本开始，先看这一页。
> 维护说明：新增设计技能时，请同步更新本页三层表与路由表。

## 一、十四个技能是什么关系

它们不是"十本并列的书"，而是**一条研发流程上的十个岗位**，分三层：

```
┌─ 第 1 层：为什么做 ──────────────────────────────┐
│  design-methodology-liuguanzong    柳冠中·事理学   │
│  world-modern-design-history       王受之·设计史   │
└──────────────────────────────────────────────────┘
                      ↓
┌─ 第 2 层：做成什么样 ────────────────────────────┐
│  design-psychology-norman          诺曼·认知与可用性│
│  ergonomics-ding-yulan             丁玉兰·人机尺寸 │
│  design-elements-hannah            汉娜·视觉构成   │
│  product-design-styling-dabbs      戴布斯·造型     │
│  visual-dynamics-industrial-design 李想·视觉动力   │
└──────────────────────────────────────────────────┘
                      ↓
┌─ 第 3 层：怎么造出来 ────────────────────────────┐
│  product-structure-liubaoshun      刘宝顺·结构     │
│  product-injection-defects         李忠文·注塑缺陷 │
│  ─────────────────────────────────────────────   │
│  solidworks-practice               实体建模·操作   │
│  solidworks-surface-advanced       曲面·原理判据   │
│  solidworks-2025-mechanical        2025版·全模块  │
└──────────────────────────────────────────────────┘

┌─ 第 4 层：视觉呈现（可选）─────────────────────────┐
│  blender-hard-surface             Blender·实战项目   │
│  blender-manual-reference         Blender·官方手册   │
└──────────────────────────────────────────────────┘
```

**第 4 层说明**：`blender-hard-surface` 是**视觉/游戏/影视**路线的建模技能，
与前面三个 SOLIDWORKS 技能（**工程 CAD** 路线）**并列而非替代**。
**同一个产品，工程要能造（SOLIDWORKS），宣传要好看（Blender）。**

**两个 Blender 技能的分工**：

| 问题 | 用哪个 |
|---|---|
| "怎么做一个机械件，从哪开始" | `blender-hard-surface`（四步工作流 + 3 个项目） |
| "这个修改器/参数到底什么意思" | `blender-manual-reference`（57 修改器 + 132 快捷键 + 术语） |
| "做金属件的参数填多少" | `blender-hard-surface`（26 项精确数值） |
| "某个功能有什么限制" | `blender-manual-reference`（官方警告与边界条件） |

**第三层的四个技能是"结构 → 软件"的工具箱**，各自分工：

| 技能 | 解决 | 何时用 |
|---|---|---|
| `product-structure-liubaoshun` | 结构**怎么成立**、用什么工艺 | 造型定稿后，判断能不能做 |
| `product-injection-defects` | 做出来**会不会有缺陷** | 塑料件投模前/出问题后 |
| `solidworks-practice` | **逐步操作**怎么做、报错怎么排 | 照书做、卡住、报错 |
| `solidworks-surface-advanced` | 曲面的**原理与判据** | 做自由曲面、判断曲面质量 |
| `solidworks-2025-mechanical` | **2025 版全模块** + 曲面命令参数 | 钣金/焊件/线路/公差分析、查参数 |

**三个 SOLIDWORKS 技能的选择**：

```
要查"这个参数干什么用"      → solidworks-2025-mechanical（ch05 曲面最全）
要查"逐步怎么点、报错原因"   → solidworks-practice
要查"曲面质量怎么判断、破面怎么修" → solidworks-surface-advanced
```

**一句话分工**：

| 问题 | 技能 |
|---|---|
| 这东西**该不该做**？做的是"事"还是"物"？ | 柳冠中 |
| 这类产品**历史上怎么来的**？别人做过什么？ | 王受之 |
| 用户会**怎么用、怎么用错**？ | 诺曼 |
| 这个**尺寸**合适吗？ | 丁玉兰 |
| 这个**形**怎么统一、有构成关系？ | 汉娜 |
| 这个造型**语言**对不对、有没有辨识度？ | 戴布斯 |
| 这个形态有**动感**吗、为什么看起来有劲？ | 李想 |
| 这个造型**能不能造出来**？用什么工艺？ | 刘宝顺 |
| 塑料件会**缩水/变形/烧焦**吗？ | 李忠文 |
| 怎么**建模、出图、装配**？ | SOLIDWORKS |

## 三、路由表：按"我现在卡在哪"找技能

### A 类：还没开始，方向不清

| 你的感觉 | 去哪 | 第一句话问什么 |
|---|---|---|
| "客户说要个更好的 X" | 柳冠中 | 这是"物"还是"事"？能不能改写成动词？ |
| "不知道这个产品该长什么样" | 戴布斯 → 汉娜 | 先定轮廓与主题，再定形体关系 |
| "同类产品都长这样，怎么不一样" | 王受之 → 戴布斯 | 查清历史脉络，再找时代精神 |
| "老板要加功能，但界面已经满了" | 诺曼 | 加功能的代价是隐藏操作信息 |

### B 类：有想法了，要推敲

| 你的感觉 | 去哪 | 关键判据 |
|---|---|---|
| "这个形看着别扭，说不出哪不对" | 戴布斯 | **先怀疑比例**——"看起来不太对劲通常由比例不完美导致" |
| "几个体块拼在一起很乱" | 汉娜 | 主导/次要/附属；次要形体使主导特征提升 20% |
| "看着没劲、太平" | 李想 | 找几何基准线的偏离趋势 = F；或加轴线运动 |
| "太飘、不稳" | 李想 | 补一个支撑要素（视觉平衡） |
| "握不住 / 够不到 / 看不清" | 丁玉兰 | 先定 Ⅰ/ⅡA/ⅡB/Ⅲ 型，再选百分位 |
| "用户老按错按钮" | 诺曼 | 匹配 + 四类限制因素；错得严重用强迫性功能 |
| "不确定这个反馈够不够" | 诺曼 | 立即、明显、看得到与前一状态的变化 |

### C 类：要做出来了，怕做不出/做坏

| 你的感觉 | 去哪 | 关键判据 |
|---|---|---|
| "这个形能不能做出来" | 刘宝顺 | 四大工艺选型 + 工艺性七问 |
| "拔模给多少" | 刘宝顺 | 内 **15′** / 外 **30′** / 筋 **2°～5°** |
| "铸件/焊接件怎么不废" | 刘宝顺 | 铸造七问 / 焊缝避开拐角 |
| "密封最后再说吧" | 刘宝顺 | **不行**——密封放最后会造成无法弥补的缺陷 |
| "安全怎么加" | 刘宝顺 | 六原理：警示/转换/借助/隔离/安全存在/有限损坏/冗余 |
| "塑料件会不会缩水" | 李忠文 | 先看壁厚均匀度，再看保压 |
| "已经出缺陷了" | 李忠文 | 决策树 → 先工艺后模具后结构 |
| "到底改参数还是改模" | 李忠文 | 三条硬判据（参数到边界/不同腔表现不同/换料就好） |

### D 类：要落地

| 你的感觉 | 去哪 | 关键判据 |
|---|---|---|
| "怎么建模" | SOLIDWORKS | 先看"分析模型"两步：摆放 + 最佳轮廓 |
| "草图改不动" | SOLIDWORKS | 蓝=欠定义、黄=过定义 |
| "照书做卡住了" | SOLIDWORKS | `walkthroughs/chXX.md` 的 `[隐]` 标记 |
| "报错了不知道原因" | SOLIDWORKS | `F-INDEX.md` 按现象查 182 条 |

### E 类：做出来了，但有问题

> **这一类与 A/B/C/D 类的区别：它不在"设计流程"里，而在"出问题之后"。**
> A 类问"该做什么"，B 类问"好不好看"，C 类问"这个缺陷怎么修"。

| 你的感觉 | 去哪 | 关键判据 |
|---|---|---|
| "塑料件表面有流痕/气纹/烧焦" | **李忠文** | 先看是多级注射哪一段的问题 |
| "缩水凹点、变形翘曲" | **李忠文** | **先看壁厚均匀度，再看保压** |
| "披锋毛边、粘模、顶白" | **李忠文** | 决策树：先工艺 → 再模具 → 最后结构 |
| "尺寸偏差、色差脏污、缺胶" | **李忠文** | 归因路径 + 工艺表解读 |
| "想知道会不会出缺陷"（还没投产） | **李忠文** | 结构端预防判据 |
| "已经改过工艺还是不行" | **李忠文 → 刘宝顺** | 三条硬判据判断该不该改模/改结构 |
| "金属件表面缺陷" | **（书中未覆盖）** | 注塑技能只讲塑料；金属缺陷需另找资料 |

**技能**：`product-injection-defects`（李忠文《精密注塑工艺与产品缺陷解决方案 100 例》）

**它的独特结构**（与其他 13 个不同）：
- `chapters/` 只有 1 个（ch00-overview）
- **主体在 `references/case-index.md`（100 例索引）+ `decision-tree.md`（决策树）**
- **案例型知识不按"章"组织，按"症状 → 案例"查** —— 这是刻意的

**三条硬判据**（判断"该调参数还是该改结构"）：
1. 参数是否**已到边界**？
2. **不同腔**的表现是否不同？（不同腔不同 → 模具问题）
3. **换料就好**？（换料就解决 → 材料问题）

> **注意时机**：**C 类应在 A/B 之后、投模之前介入**——
> 结构定稿后用它的"结构端预防判据"过一遍，比出问题再修便宜得多。

## 四、跨技能的六个"接缝"（最容易掉东西的地方）

技能之间真正的风险不是"没调用"，而是**交接处没人负责**。

| # | 接缝 | 会掉什么 | 怎么接 |
|---|---|---|---|
| 1 | **柳冠中 → 其他人** | 没人质疑"要不要做这个产品" | 项目启动先过一遍内外因，别直接进造型 |
| 2 | **诺曼 ↔ 戴布斯** | 好看但不好用，或好用但难看 | 诺曼的"反馈/可视性"要作为造型的**约束**，不是事后补 |
| 3 | **丁玉兰 ↔ 汉娜** | 比例好看但尺寸不成立 | 先定人机尺寸区间，再在此区间内推比例 |
| 4 | **造型 → 刘宝顺** | 造型给的是"好看"标准，不是"能做"标准 | 造型定稿后用**结构评审清单**过一遍（拔模/壁厚/圆角/分型） |
| 5 | **刘宝顺 → 李忠文** | 结构对了，注塑还是会出缺陷 | 结构特征 → 缺陷类型的对照表 |
| 6 | **结构 → SOLIDWORKS** | 方案对但建模顺序错，后面改不动 | 分件决定零件数，分型面决定基准面 |

完整的接缝说明见 `product-structure-liubaoshun/references/design-pipeline.md`。

## 五、三种典型任务的调用组合

### 场景 1：从 0 做一个新产品

```
柳冠中（该做什么）
  → 王受之（历史参照，可选）
  → 诺曼（怎么用）+ 丁玉兰（尺寸）
  → 戴布斯（轮廓主题）→ 汉娜（形体关系）→ 李想（动感）
  → 刘宝顺（结构 + 工艺选型）
  → 李忠文（注塑风险评估）
  → SOLIDWORKS（建模出图）
```

### 场景 2：已有产品要改款

```
王受之（原型的来历）→ 戴布斯（轮廓与配置图，先理解为何长这样）
  → 李想（改完有没有更弱/更强）
  → 刘宝顺（改款会不会动到结构）
  → SOLIDWORKS（改模型）
```

### 场景 3：量产出了问题

```
李忠文（先看缺陷类型与对策）
  → 若判断是结构问题 → 刘宝顺（改结构）
  → 若判断是人的使用问题 → 诺曼（改交互/防错）
  → SOLIDWORKS（改模/改模型）
```

## 六、什么时候**不要**串起来

原书自己提醒过的三处"不必"：

- 刚度强度**不必**自己算——刘宝顺明说"通常需要结构工程师配合"
- 密封**不必**追求绝对——"对很多产品也没有必要，而且还要考虑成本"
- 一次性/不维修产品**不必**设计可拆结构

同理：
- 简单产品不必做完整人机计算（丁玉兰的百分位法用于有明确人机界面的产品）
- 造型已有明确传承的不必查设计史
- 结构极简单的零件不必过完整结构评审

> **串技能是为了不漏，不是为了走流程。** 按复杂度裁剪。

## 七、常见误用

| 误用 | 后果 | 纠正 |
|---|---|---|
| 用造型技能做"该不该做"的判断 | 越做越漂亮但方向错 | 方向归柳冠中 |
| 用诺曼的标准评价形态美 | 好用但平庸 | 美归汉娜/戴布斯/李想 |
| 让造型决定工艺 | 做不出来 | 工艺归刘宝顺 |
| 结构定完才想密封 | **无法弥补的缺陷** | 密封一开始就纳入 |
| 出缺陷就改结构 | 成本最高 | 先调工艺（李忠文的顺序） |
| 把 SOLIDWORKS 当设计工具 | 会建模但不会设计 | 它只负责落地 |

检查两项：**数字一致性**（标题声明 vs 速览表行数）与**编号唯一性**（`### X 类：` 是否重复）。

#### 8.3.2 页码引用（`validate-page-citations.py`）

> **背景**：从纸质书蒸馏的技能，正文大量用 `（p123）` 标原文出处。
> 这类引用有三个肉眼难查的缺陷，本项目**每种都真实发生过**：

| 缺陷 | 真实案例 |
|---|---|
| **页码越界** | 引用 `p137`，但全书只到 p136 |
| **格式混用** | 同一技能内混用 `p12` 与 `p012` |
| **未实读引用** | 页码来自二手转述，从未核对原页 |

**用法**：
```powershell
# 查越界与格式（不需要 manifest）
python validate-page-citations.py --skill product-structure-liubaoshun

# 用 manifest 查"未实读引用"
python validate-page-citations.py --skill XXX

# 全部技能
python validate-page-citations.py --all

# 生成 manifest 模板
python validate-page-citations.py --skill XXX --init-manifest
```

**manifest 放哪**：`<技能>/references/page-manifest.json`
```json
{
  "book": "《产品结构设计》刘宝顺，中国建筑工业出版社，2005",
  "page_range": [9, 136],
  "read": [9, 10, 11, "..."],
  "note": "p136 为参考文献页"
}
```

**退出码**：0 通过 / 1 有 ERROR。

> **★ 已实测抓到的真实缺陷**（product-structure-liubaoshun）：
> - `SKILL.md:29` 引用 `p131–137`（**越界**）→ 实际第六章是 p129-p135
> - `cheatsheet.md:82` 引用 `p137`（**越界**）→ 积极冗余在 p135
> - `glossary.md` 4 处引用了 p136/p137 → 实际 p134/p135
> - **86 处两位格式** `pNN` → 统一为三位
>
> **这些缺陷全部是手工写作时引入的，肉眼审阅 5 遍也没发现。**

#### 8.3.3 回归测试（`test-validate-skill-index.py`）

> **为什么需要**：`cn2int` / `int2cn` 是本项目最容易"静默出错"的代码。
> 已实测到三类问题，**全部靠测试才抓出来**：

| 类型 | 实例 | 后果 |
|---|---|---|
| 静默算错 | `"一万三千"` → 3000 | 数字看似合理，自检兜不住 |
| 边界崩溃 | 辅助函数漏定义 | 1..105 正常，**110 起 NameError** |
| 非法输入被接受 | `"十十"` → 20、`"十百"` → 110 | 非规范数词被当成有效值 |

**用法**：
```powershell
python test-validate-skill-index.py           # 全部（含 1..99999 往返，约 3 秒）
python test-validate-skill-index.py -v        # 逐用例显示
python test-validate-skill-index.py --quick   # 跳过全量往返（不推荐）
```

**测试覆盖**（92 个断言）：
| 组 | 内容 | 数量 |
|---|---|---|
| ① | `cn2int` 中文/阿拉伯 → 整数 | 40 |
| ② | 裸量词（只有「十」允许） | 5 |
| ③ | 非法写法 → None | 12 |
| ④ | `int2cn` → 中文（规范写法） | 26 |
| ⑤ | 标题「N 个技能」解析 | 9 |
| ⑥ | **1..99999 全量往返** | 1 |

**★ 第 ⑥ 组是核心**：`int2cn(n)` 转成中文，再 `cn2int` 转回，必须等于 n。
这能一次性覆盖所有边界（10/100/1000/10000 附近、连续零、单位顺序）。

> **实测教训**：我第一次只测到 105 —— 正好跳过了 110 那个崩溃点。
> **测试范围必须越过你直觉认为的边界。**

### 8.4 写扫描类工具时的两条铁律（都是真实踩坑）

> 这两条来自 2026-11-12 给 `validate-page-citations.py` 加功能时的两次误报。
> **误报比漏报更消耗信任**——一次假 ERROR 会让人开始怀疑所有 ERROR。

#### 铁律 1：格式不统一会连带破坏"范围统计"

| | |
|---|---|
| **现象** | 用 `p(\d{3})` 统计页码范围，得到 [145,921]；跑出 **180 个假 ERROR**（如 `p11–69` 被判越界） |
| **根因** | 该技能里存在 `p11`（**两位**）写法，三位正则匹配不到 → 下限被算成 145 而非 11 |
| **正确做法** | 范围统计用 **`p(\d{2,3})`**；格式检查才用 `p(\d{3})` / `（p(\d{1,2})）` |
| **推广** | 只要允许两种写法共存，**任何只认一种写法的统计代码都会漏数据** |

> **所以"统一格式"不是美观问题，它是数据正确性的前提。**

#### 铁律 2：元文档必须排除在单技能扫描之外

| | |
|---|---|
| **现象** | CHANGELOG 里记了各技能页码范围（`p13–p207`），再跑 `--all` 报 **784 个假 ERROR** |
| **根因** | CHANGELOG 是**元文档**，它引用的是**别的技能**的页码 |
| **正确做法** | 维护 `META_FILES` 排除集合；确需检查用 `--include-meta` |
| **推广** | **"记录内容"的文档（日志/索引/总览/规范）与"被记录的内容"必须分层** |

> **判断标准**：这个文件是在**讲内容**，还是在**记录内容**？后者一律排除。

**当前 `META_FILES` 清单**：`changelog.md` / `before-after.md` / `skill-catalog.md` / `skill-index.md` / `standard.md`
——**新增元文档时记得往集合里加**。

#### 静默失效：三种形态与对策（2026-11-12 第二次改造）

> 上一轮把"只认中文数字"改成"兼容阿拉伯"，但仍有 **两种静默失效** 没解决。
> 实测确认后一并修掉，并加了自检。

| # | 形态 | 表现 | 对策 |
|---|---|---|---|
| **1** | **数字超出解析范围** | `cn2int("二十一")` 返回 None → `if n:` 判假 → **整项检查跳过** | 放弃硬编码字典，改**算法解析**（支持到 9999） |
| **2** | **序号前缀不匹配** | `## 1. 14 个技能` / `## （一）14 个技能` / `## 第1章 14 个技能` **全部抓不到** | 前缀改为**贪婪匹配**，锁定紧邻"个技能"的数字 |
| **3** | **抓不到但无人知** | 上述两种情况**退出码仍是 0**，显示"全部通过" | **新增自检**：无法解析就报 WARN，并列出文件行号 |

**三条对策的共同原则**：

> **宁可 WARN，不可静默。**
> 一个检查工具最坏的状态不是"报错太多"，而是"**看起来在跑，其实没查**"。

**实测对比**（同一份错误文档：声明 21 个、表 2 行）

| 版本 | 结果 |
|---|---|
| 改造前 | 退出码 **0**，"全部通过"（完全漏掉） |
| 改造后 | `[ERROR] 标题声明「二十一个技能」但速览表实际 2 行`，退出码 **1** |

**实测 8 种章节写法**（改造后全部命中）：

```
## 一、14 个技能速览          ✓
## 1、14 个技能速览           ✓
## 1. 14 个技能速览           ✓
## （一）14 个技能速览         ✓
## 第1章 14 个技能速览         ✓
## 二十一、21 个技能速览        ✓
## 1.5 节 14 个技能速览        ✓
## 二、十四个技能是什么关系      ✓
```

#### 铁律 1 的实例：中文数字 → 兼容阿拉伯数字（2026-11-12）

> 铁律 1 说"格式共存会破坏统计"，**这不只是页码脚本的事**。
> `validate-skill-index.py` 原本也只认中文数字，同一个毛病。

| | |
|---|---|
| **隐患** | 原正则只匹配 `[一二三四五六七八九十]+`，"## 二、**14** 个技能速览"抓不到 |
| **后果** | 数字一致性检查**静默失效**——不报错，直接当作"没声明"跳过 |
| **修复** | 统一用 `NUM_PAT = (?:[一二三四五六七八九十]+|\d{1,2})`，两写法全吃 |
| **`--fix-numbers`** | 另加"**保持原写法**"：中文改完仍中文，阿拉伯改完仍阿拉伯 |

> **★ 最危险的不是报错，是静默跳过。**
> 只认一种写法的解析代码不会崩，它只会**悄悄算出错误结果**，
> 让你误以为"检查通过了"。
>
> **这比假 ERROR 更隐蔽**——假 ERROR 至少会引起注意。

#### 写新扫描工具前的四问

> 本项目的扫描类脚本都有"误报"风险。写新的之前先过这四问：

| # | 问自己 | 若答案是"是" |
|---|---|---|
| 1 | 要统计的数据，**在源文件里有几种写法**？ | 正则必须全吃（如 `\d{2,3}`），否则漏数据 → 假越界 |
| 2 | 要扫的文件里，**是否有"记录其他对象"的元文档**？ | 加进 `META_FILES` 排除，或单独开关 |
| 3 | 我的规则会不会**在正常情况下报警**？ | 先拿已知正确的样例跑一遍，**0 ERROR 才算规则可用** |
| 4 | 报错信息里**能否一眼看出该改哪里**？ | 输出必须带 `文件:行号` + 原始片段 |

> **第 3 条最重要**：新规则上线前，**先在一个"已知全对"的技能上跑**。
> 若它对正确数据报警，规则本身就是错的——此时应改规则，**不要改数据**。

### 8.5 目标："每个页码都读过"的可验证性

改了本页之后，跑一次：

```powershell
python "<skills>/design-methodology-liuguanzong/references/validate-skill-index.py"
```

**退出码 0 = 通过，1 = 有 ERROR。**

它检查两项（对应 8.2 最容易漏的地方）：

| # | 检查 | 抓什么 |
|---|---|---|
| **1** | **数字一致性** | 标题声明的技能数 vs 速览表行数；表内字数 vs 实测；**速览表是否漏了全文提到过的技能** |
| **2** | **编号唯一性** | `### X 类：` 字母是否重复、是否连续 |

**参数**：
- `--skills-root <路径>` 指定 skills 根目录（默认自动推断）
- `--fix-numbers` 按速览表行数自动改标题里的中文数字

> **写这个脚本的起因**：8.2 定了「改了就记」，但**没有任何机制强制检查数字是否同步**。
> 脚本第一次跑就查出 **2 个 ERROR**（速览表漏了 2 个 Blender 技能，标题却写"十四个"）
> 和 **4 处字数过时**——**全是我之前手工改漏的**。
