## 一、一句话结论

> **仓库是干净的 LF（索引 `i/crlf = 0`）。**
> **本机工作区有 104 个文件显示 `w/crlf`，这是 `core.autocrlf=true` 的检出表现，不是缺陷，不要修。**
> **不要添加 `.gitattributes`。**（2026-11-17 用户明确决定：保持现状）

## 二、编码约定（当前状态）

| 项 | 约定 | 当前实测 |
|---|---|---|
| **文件编码** | UTF-8，**不带 BOM** | BOM = 0 |
| **行尾（索引）** | **LF** | `i/lf = 532`、`i/crlf = 0`、`i/mixed = 0` |
| **行尾（工作区）** | 由 `core.autocrlf=true` 决定，**允许 CRLF** | `w/lf = 428`、`w/crlf = 104` |
| **`.gitattributes`** | **不添加** | 不存在 |

### 复跑校验

```bash
node "D:\deepseek 工作\_zl\encoding_audit.js"   # BOM / stray U+FEFF / invalid UTF-8 / 混用行尾
node "D:\deepseek 工作\_zl\eol_diagnose.js"     # 索引 vs 工作区的行尾分布
```

判据：
- `[1] leading BOM` 必须为 **0**
- `[3] invalid UTF-8` 必须为 **0**
- `[4] MIXED=0`（同一文件内 CRLF 与 LF 混用，这是唯一要修的行尾问题）
- `index 中 crlf/mixed` 必须为 **0**

## 三、为什么 `w/crlf` 不需要修（实测依据）

### 3.1 三条证据

**证据 1：索引里根本没有 CRLF**

```
$ git ls-files --eol | 统计
i/lf    = 532
i/crlf  = 0      ← 关键
i/mixed = 0
```

`i/` 是索引（真正提交的内容）。`i/crlf = 0` 意味着**任何人 clone 到的都是 LF**，仓库未被污染。

**证据 2：`git diff` 为空，且原因是可解释的**

以 `solidworks-2025-mechanical/chapters/ch01-interface.md` 为例：

```
磁盘上 CRLF           : 1278 个
索引 blob 里 CRLF     : 0 个
─────────────────────────────────────────
hash-object (应用 filter)  = e97244b6...   ← 与索引相同
hash-object (--no-filters) = 397cd52c...   ← 与索引不同
索引 blob                  = e97244b6...
```

`git hash-object` **默认走清楚过滤器**，先把 CRLF 归一成 LF 再算哈希。
所以「归一后内容 == 索引内容」→ diff 为空。
磁盘字节确实不同，但 **git 认为语义未变**。

**证据 3：曾经"修"过一次，git 什么都没记录**

2026-11-17 曾把 9 个混用行尾的文件统一成 LF 并提交，
`git show --stat` 显示 **只有 3 个文件**（2 个 BOM + 1 个内容修复），
那 9 个文件**一个都没进提交** —— 因为 git 归一化后判定无变化。

> **★ 教训：在 `autocrlf=true` 下，逐文件改工作区行尾是无效操作。**

### 3.2 那 104 个文件长什么样

- 其中 **90 个是 `.md`**
- 分布：`solidworks-practice` 13、`solidworks-2025-mechanical` 12、
  `design-methodology-liuguanzong` 11、`solidworks-surface-advanced` 10、
  `blender-manual-reference` 9 ……
- **没有一个是本轮新建的技能**（node 写出的文件天然是 LF）

即：CRLF 全部是**历史遗留 + 本机检出产物**，与内容正确性无关。

## 四、为什么不用 `.gitattributes`（三个方案对比）

| 方案 | 做法 | 后果 | 采用 |
|---|---|---|---|
| **A. 改 `core.autocrlf=false` 并重新检出** | 本机配置 | 只影响本机，不同步给任何人；Windows 上不加 `.gitattributes` 会回退 | ❌ |
| **B. 加 `.gitattributes` 写 `* text=auto eol=lf`** | 写进仓库 | 所有协作者下次检出产生**104 文件全量重写**式 diff；有人存成 CRLF 就会永久显示"已修改"，每次提交都要 `--renormalize` | ❌ **用户已决定不加** |
| **C. 逐文件强制改字节** | 直接改工作区 | **无效**（见 §3.1 证据 3），git 归一化后判定无变化 | ❌ |

### 决定性理由

**这是一个知识库，不是需要跨平台编译的代码仓库。**

- 1044 个 md / 约 1500 万字
- 行尾对 markdown 渲染**无影响**
- 对项目内所有校验脚本**无影响**（脚本均 `\r` 兼容，且统计时先 `replace(/\r\n/g,'\n')`）

为一个不影响任何实际行为的显示项，引入 104 文件 diff + 一次配置风险，**不划算**。

## 五、BOM 的历史教训（这个是真要修的）

BOM 与 CRLF 不同：**BOM 会真实进入仓库并破坏首行**。

| 事实 | 说明 |
|---|---|
| 危害 | 首行变成 `\uFEFF#`，导致 markdown 一级标题解析失败、锚点脚本失效 |
| 累计发现 | 第 1 批 14 个（`web-accessibility-cn` 全部章节 + glossary + patterns） |
| 第 2 批 | 2 个（`solidworks-2025-mechanical` 的 ch01、ch02）—— 老文件遗留 |
| 根因 | PowerShell `Set-Content -Encoding utf8` **会写 BOM**（Windows PowerShell 5.x 行为） |
| 修法 | 读字节，若前三字节为 `ef bb bf` 则丢弃，以 `Buffer` 写回 |

**实测确认 BOM 已从提交对象移除**：

```
ch01  HEAD~1 bytes=92411 BOM=true  →  HEAD bytes=92408 BOM=false
ch02  HEAD~1 bytes=174304 BOM=true →  HEAD bytes=174301 BOM=false
首 8 字节: 23 20 e7 ac ac 20 31 20   (23 = '#')
```

### 往后写文件的规矩

| 场景 | 做法 |
|---|---|
| **写 md** | 用 `write` 工具，或用 node `fs.writeFileSync`（都不写 BOM） |
| **PowerShell 写文本** | 用 `[System.IO.File]::WriteAllText($p, $t, [System.Text.UTF8Encoding]::new($false))`，**不要用 `Set-Content -Encoding utf8`** |
| **提交前** | 跑一次 `node _zl\encoding_audit.js`，确认 `[1] leading BOM = 0` |

## 十一、2026-11-17 第 7 项检查：判据编号连续性

### 11.1 这一项花了 10 版才收敛，过程本身是结论

| 版本 | 假设 | 误报数 | 为什么错 |
|---|---|---|---|
| v1 | 遇到非编号行就断段 | 152 | 表内的分隔行把一张表切成多段 |
| v2 | 按 markdown 表格块分段 | 146 | 漏认粗体编号 `\| **12** \|` |
| v3 | 一个文件 = 一条序列 | 15 | 同文件有多条独立序列 |
| v4 | 每张表从 1 起 | 495 | 子表合法地续接总表编号 |

| v6 | 按小标题分组 | 451 | 小标题下的表也会跨小标题续接 |

> **★ 教训：连续 9 版都在"调整规则让数字变小"，而真正的问题只有一个类型。**
> **第 10 版改了思路——不问"编号是否全连续"，改问"哪一处会误导读者"。**

### 11.2 为什么"编号全连续"是个错误的目标

本库**同时存在**三套合法编号习惯，且常在同一个文件里混用：

```
//  ## 1.5 四步建模工作流        | **1** | .. | **4** |   ← 独立小表
//  ## 1.6 三个项目的难度递进    | **1** | .. | **3** |   ← 又一独立小表
//  ## 1.8 本章判据总表（共 32 条）
     ### 定义与分类          | 1 | .. | 4 |
     ### 四类技术判据        | 5 | .. |19 |            ← 续接上一段
```

这三套都对。**任何"必须全连续"的规则都会把这些正确写法判错。**

### 11.3 改查两个"真会误导读者"的指标

**① 同一张表内编号重复** —— 读者会看到两个「1」。

```
整数编号表 1088 个  →  重复编号 0 处
```

**② 标题声明「共 N 条」与实际行数不符** —— 这是**硬声明**，可以严格核对。

```
「共 N 条」声明 197 处  →  不一致 0 处（修完 16 处之后）
```

### 11.4 修掉的 16 处（全部是上一轮漏改标题）

| 技能 | 处数 | 声明 → 实际 |
|---|---|---|
| `inclusive-accessibility-design` | 8 | 14→22、16→19、17→21、15→19、16→26、15→18、18→25、16→28 |
| `web-accessibility-cn` | 7 | 22→29、22→28、22→32、18→26、20→28、20→35、14→24 |
| `usability-testing` | 1 | 24→30 |

典型例：`ch02` 标题写「共 14 条」，实际表里有 **22 条** ——
这是我上一轮把表补长了、却没回头改标题。

### 11.5 一个必须说明的误判与更正

`web-accessibility-cn` 的 WCAG 表写「共 61 条」，我的整数计数器读出 **0 行**，一度判为"差 -61"。

实际查证：该表用**点分编号** `1.1.1 / 1.2.3`，不是整数；表中
- **成功准则行 61 条**（正是声明的 61）
- 另有指南行 12 条（`1.1`、`1.2` 这种）

**声明是对的，是我的计数器不认点分编号。** 加入点分样式识别后降为 0 处误报。

> **★ 这是本轮第 N 次"脚本错、内容对"。凡是范式差异（整数 vs 点分、明码 vs 粗体），
> 先怀疑解析器。**

### 11.6 结论

> **★ 判据编号的真实质量：1088 张表 0 重复、197 处声明 0 不符。**
> **★ 但「编号是否跨表连续」不是缺陷指标，本库不统一该习惯，也不需要统一。**

## 十三、2026-11-17 第 9 项检查：章节页码覆盖率

### 13.1 最初的想法（错的）

原计划：统计每章声明的页码范围 `pXXX–pYYY` 里，实际引用覆盖了百分之几。
**第一版跑出 69 章"引用了范围外页码"、47 章覆盖率 <50%** —— 看起来问题很大。

逐个核实后发现**全是误判**，原因有三类：

| 现象 | 真相 |
|---|---|
| `ergonomics-ding-yulan` 每章都"越界 ±12 页" | 该技能明写 **`书内页 = PDF 页 − 15`**，我拿书内页去比 PDF 页 |
| `product-injection-defects` 同样 | 明写 **`书内 p2–p22 = PDF[7]–PDF[27]`** |
| `inclusive-accessibility-design` 大幅越界 | 它声明的是**两本书**的范围（Clarkson ＋ Coleman），我只取了第一本 |
| `solidworks-2025-mechanical` 全 14 章"零引用" | 它用 **`PDF[123]`** 格式，我的正则只认 **`（p123）`** |

第三类最典型：该技能实际有 **487 处 `PDF[N]` 引用，覆盖 11–138 页**，
而我的检测器报告"0 个页码"。

### 13.2 第二个想法（也不对）

修正口径后再看，仍有 12 章"大量引用落在声明范围外"。逐条读原文，例如：

```
cmf-system/ch03 声明 p42–p108，却引用 p129 / p247 / p261
  实际内容：> | 色彩与材料的耦合（发色机理）| **有强内容**（p247、p254、p261）|
```

这是**跨章引用**："本章主体读 p42–p108，但论证时顺带引了后面章节的段落"。
**章节声明的是"我把哪些页当作本章正文读"，不是"我只许引这些页"。**

> **★ 所以"引用越界"根本不是缺陷指标。**

### 13.3 最终指标（只有这两条是真会出错的）

**① 声明的页数 与 pA–pB 的实际跨度是否一致**

标题常写 `PDF[11]–PDF[69]（共 59 页）`。若 69−11+1 ≠ 59，就是笔误。

```
[a] 「（N 页）」与实际跨度不符: 0 处
```

**② 声称"逐页读完全部 N 页"，但该范围内一个页码都没引**

这是**不可验证的声明**——说了读过却没有任何页码锚点。

```
[b] 声称逐页读完但范围内零引用: 0 处
```

### 13.4 结论

| 指标 | 值 |
|---|---|
| 章节文件 | 195 |
| 有页码声明 | 111 |
| 页数声明与跨度不符 | **0** |
| 逐页读完声明不可验证 | **0** |

> **★ 页码体系是自洽的：声明多少页 = 实际跨度多少页，且每章都能在声明范围内找到引文锚点。**
> **"覆盖率不足"是伪指标——章节本来就允许跨章引用。**

### 13.5 三次口径修正的顺序（可复用的排查路径）

```
第一版：只认 （pN）           -> solidworks-2025 全部误判为"零引用"
第二版：加上 PDF[N]           -> 误判消失，但仍报 12 章"越界"
第三版：认清"越界"是跨章引用   -> 换指标，归零
```

> **★ 每当一个指标跑出"大面积异常"，先假设是口径不匹配，再假设是内容有问题。**
> **大面积 ≠ 严重，大面积多半意味着规则错了。**

| 准则 | 级别 | 一般文字 | 大字号 | 对象 |

| **1.4.3 Contrast (Minimum)** | AA | **4.5:1** | **3:1** | 文字与文字图像 |
| **1.4.6 Contrast (Enhanced)** | AAA | **7:1** | **4.5:1** | 文字与文字图像 |
| **1.4.11 Non-text Contrast** | AA | **3:1** | — | UI 组件边界与状态、必要图形 |

**关键**：`3:1` 在 WCAG 里出现**两次**，指**两个不同对象** ——
1.4.3 的 3:1 是「大字号文字」，1.4.11 的 3:1 是「非文字」。`4.5:1` 同样出现两次（一般文字 AA / 大字号 AAA）。

| 技能 | 它的表述 | 与原文一致？ |
|---|---|---|
| `web-accessibility-cn` ch07 | 正文 4.5:1(AA)/7:1(AAA)、大字号 3:1(AA)/4.5:1(AAA) | **✓** |
| `accessibility-standards` ch01 | 1.4.11 非文字 3:1；2.0 只管文字 4.5:1 不管控件边框 | **✓** |

**两边还互相指向**：`accessibility-standards` 说"设计用法见 `web-accessibility-cn` ch07"；
`web-accessibility-cn` 说"数值判据在 ch07，本技能不在此处重述"。**分工比合并更好。**

**② 严重度两套口径 —— 已知差异，已在 USAGE-GUIDE 显式裁决**

`usability-testing` ch08 §8.4（Rubin，4 最重）与 §8.5（Barnum，1 最重）方向相反，
但这是**同一技能内部的两套并列口径**，不是跨技能冲突。
裁决已写进 `design-router/references/USAGE-GUIDE.md` 的「C-2 附」。

### 14.5 结论

| 指标 | 值 |
|---|---|
| 跨技能共享原文（≥30 字） | **1 条** |
| 该条的表述一致性 | **一致** |
| 对比度表述 | 两技能均与 WCAG 原文一致，无冲突 |
| 严重度口径 | 技能内部并列，已裁决，非跨技能问题 |

> **★★★ 结论：未发现跨技能内容冲突。**
> **但这不等于"绝对没有"—— 它意味着"用可自动化的手段查不出冲突"。**
> **真正可能藏着冲突的地方是"同一事实被两个技能用不同措辞各说一遍"**（没引原文、数值藏在句子中间），
> **那种只能靠人工读，本轮没有做。**

### 15.3 怎么还原的（没有 git，靠原始源码）

### 15.6 三个教训

> **★★★ 一、动手前先看 `.gitignore`。**
> 一个目录被忽略，往往意味着"所有权不在这里"——不是"这里没人管，可以随便改"。

> **★★★ 二、批量正则替换前，先用它匹配一遍全文并抽样人眼核对。**
