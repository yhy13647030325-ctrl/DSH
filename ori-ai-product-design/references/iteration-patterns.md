# 迭代模式参考

> 从真实产品迭代中提炼的典型场景、踩坑经验和最佳实践。
> AI 在执行阶段应参考此文件，避免重复踩坑。

---

## 1. 典型迭代场景

### 1.1 从方案文档到产品原型

**场景**：PM先输出了文字版产品方案（.md），再要求转化为可交互的HTML原型。

**正确做法**：
1. 完整精读方案文档（不跳读）
2. 提取结构化信息：模块列表、指标定义、计算公式、分类标签
3. 确认与PM："我从文档中提取了XX个模块、XX个指标，信息架构如下，是否准确？"
4. 先搭全局骨架（所有页面路由+导航），再逐页填充

**常见错误**：
- 只看文档摘要就开始做，遗漏细节
- 方案中的定性描述被AI错误量化
- 文档中的"建议"被AI当作"确定需求"执行

### 1.2 外部方法论融入

**场景**：PM提供了一份外部研究报告（如竞品分析、行业白皮书），要求融入产品设计。

**正确做法**：
1. 逐字精读（尤其是数据、公式、阈值）
2. 提取6-8个可落地的要素
3. 向PM确认："这份报告的核心结论我理解为XX，计划落地方式是YY"
4. 适配而非照搬（同一个公式在不同平台的参数可能不同）

**实战案例**（热度监播项目）：
```
输入：某平台社交互动加热策略研究报告
提取要素：
- 互动正循环模型 → 落地为加热四象限分类逻辑
- 生命周期数据（短周期→长周期）→ 落地为热度值范围参考表
- 涟漪效应公式 → 落地为后台配置的权重设计依据
- 多渠道配比 → 落地为加热建议卡片的策略推荐
```

### 1.3 指标体系迭代

**场景**：PM对现有指标计算方式不满意，要求调整。

**正确做法**：
1. 理解PM的不满来源（是数值量级不对？还是排序结果不合理？）
2. 提供2-3个调整方案，带样本数据验算
3. PM选定后，确保**所有使用该指标的模块同步更新**（指标卡、趋势图、排行榜、标签判断）
4. 清除缓存（如 `_enrichedCache = null`），确保全局一致

**关键原则**：指标逻辑变更是全局性的，不能只改一个展示点。

### 1.4 UI风格微调

**场景**：PM对某个UI细节不满意，要求调整。

**常见类型及处理**：

| PM说 | AI应该做 |
|------|---------|
| "这个按钮太突兀" | 降一级：primary→outline 或 outline→ghost |
| "不要用emoji" | 替换为同义SVG图标 |
| "选中态不明显" | 底部指示条/边框高亮/颜色加深（不加背景填充） |
| "太挤了" | 增加padding/gap，检查是否影响响应式 |
| "颜色不对" | 精确对齐设计系统色阶，不自创颜色 |
| "感觉不高级" | 减少装饰、增加留白、统一圆角、弱化阴影 |

## 2. 踩坑经验

### 2.1 代码层面

| 踩坑场景 | 经验教训 |
|---------|---------|
| DOM还没渲染就getElementById | 初始化阶段所有DOM操作加null保护 |
| 箭头函数在老浏览器报错 | 初始化和事件处理用function声明 |
| Chart.js重建前未销毁旧实例 | 维护全局chart引用数组，重建前destroy |
| sparkline forEach某个元素已被移除 | 整个forEach用try-catch包裹 |
| localStorage存了损坏的JSON | load函数整体try-catch，损坏时回退默认值 |
| date字符串split后NaN | 加parseInt+isNaN校验 |
| 多处使用同一计算但口径不一致 | 抽为DataStore方法，所有模块统一调用 |

### 2.2 设计层面

| 踩坑场景 | 经验教训 |
|---------|---------|
| 深色模式有白底元素 | 不用`#fff`和`white`，全部用CSS变量 |
| 数字表格不对齐 | 加`font-variant-numeric: tabular-nums` |
| 标签颜色在深色模式不可读 | 深色下用浅色文字+深色背景变体 |
| 渐变球在配色方案切换后颜色不对 | 每个palette单独定义body::before/::after |
| 表格在窄屏溢出 | 外层加`overflow-x: auto` |

### 2.3 业务逻辑层面

| 踩坑场景 | 经验教训 |
|---------|---------|
| Demo数据热度值与播放量级不匹配 | 热度值由公式实时计算，不硬编码 |
| 话题排序后排名序号未更新 | 排序函数末尾重新渲染排名 |
| 筛选后指标卡片数字未变 | 确保筛选器变更触发syncAllViews |
| 强插话题参与热度排序 | 强插话题单独处理，不进入排序逻辑 |
| 环比计算除以零 | 上期为0时显示"N/A"而非Infinity% |

## 3. 高效迭代的经验法则

### 3.1 迭代顺序建议

```
骨架 → 数据逻辑 → 核心页面 → 次要页面 → UI打磨 → 响应式 → 最终验收
```

不要在骨架阶段纠结UI细节，也不要在UI打磨阶段改数据结构。

### 3.2 PM-AI沟通效率

- **截图 + 一句话** > 长段文字描述
- **"把A改成B"** > "A好像不太对"
- **一次改一个点** > "把这5个问题一起改了"
- **给正向参考** > "我不喜欢这个"（但不说喜欢什么）

### 3.3 AI自检习惯

每次改动后，AI 应自动执行：
1. 检查深色模式下改动处是否正常
2. 检查改动是否影响了其他模块
3. 检查响应式断点下是否正常
4. 如果涉及数据逻辑，输出一组验算结果

### 3.4 何时建议PM停下来

AI发现以下情况时，应主动提醒PM：
- 同一个地方来回改了3次以上 → 可能需要重新定义需求
- 数据逻辑已经非常复杂但仍在单HTML中 → 建议拆分或引入构建工具
- 文件体积超过300KB → 考虑代码分块或精简
- PM的反馈开始矛盾（这次说A好，下次说A不好）→ 需要对齐标准
