## P1 查一个条目的级别与阈值

**输入**：一个条目号（如 `2.5.8`）或一个主题（如『触摸尺寸』）

**步骤**：

1. 若是条目号 → 打开 `cheatsheet.md` 第一/二/三节的表，或直接读 `chapters/ch01`（2.1）／`ch02`（2.2）
2. 若是主题 → 走 `SKILL.md` 的『主题索引』
3. 想验证 → 跑脚本核对：

```bash
node _standards/verify_sc_coverage.js
```

**判定**：能同时答出**四项**才算查到 —— ① 条目号 ② 英文名 ③ 级别（A/AA/AAA）④ 阈值或判据。
缺任一项＝没查到，继续查。

**出处**：`chapters/ch01` §1.3、`ch02` §2.4 的判据表（每行都带级别与阈值）。

> **★ 常见错误**：只答『24 像素』不答级别。做 AA 与做 AAA 是两件事。

## P2 写一条可采购的规格条款

**输入**：产品类型 + 目标市场（欧洲 / 中国 / 通用）

**步骤**：

1. **先判市场**：
   - 欧洲公共部门 → 以 **EN 301 549** 为主，条款号直接引用
   - 无特定市场 → 界面层用 **WCAG 2.2 AA**，实物层借 **EN 301 549 第 5/8 章**
   - 中国 → 见 P9 与 ch07（**不要写 GB/T 37668 的条文**）
2. **只引 `shall` 条款写强制项**，`should/recommended` 写建议项并明确标注
3. **每条写成『前置条件 + 测试方法 + 通过判据』三段**
4. 加一句版本锁定：『本规格依据 EN 301 549 v3.2.1（锁 WCAG 2.1）』

**判定**：拿给你的条款，第三方能否**不问你**就判定通过/不通过？
不能 → 条款不可执行，回到步骤 3。

**出处**：`ch04` §4.4.1（self-scoping 与 Annex C）、§4.2.6（shall vs should）。

> **★ 反例**：『应符合无障碍要求』—— 无前置条件、无测试方法、无判据，不可执行。
> **正例**：『无遮挡向前触及范围内，至少每类操作件各一件距地 **≤1220 mm** 且 **≥380 mm**；测试：卷尺测量操作区地面至操作件中心高度（EN 301 549 8.3.2.1/8.3.2.2，shall）。』

## P3 判断某条目该不该测（版本相对性判定）

**输入**：条目号 + 你的合规声明所引用的标准版本

**步骤**：

1. 查该条目在你**所引用版本**里的状态（`ch08` §8.2 的 87 行表有『引入版本』列）
2. 若标准是 EN 301 549 v3.2.1 → **一律按 WCAG 2.1 判定**（该版锁 2.1）
3. 若条目在某版本被废止 → 检查是否有**其他引用源**仍要求它

**判定**（以 4.1.1 为例）：

| 你的声明引用 | 4.1.1 要不要测 |
|---|---|
| WCAG 2.0 AA | **要** |
| WCAG 2.1 AA | **要** |
| WCAG 2.2 AA | **不要** |
| EN 301 549 v3.2.1 | **要**（9.4.1.1 逐条转引 2.1） |

**出处**：`ch02` §2.3.3、§2.3.4；`ch04` §4.4。

> **★★★ 判据：同一个条目合不合规，取决于你声称符合哪一版。**
> 这是本技能最重要的一条方法论 —— 所有『废止』类问题都按这个套路解。

## P4 把 WCAG 条目迁到实体产品

**输入**：一条 WCAG 条目

**步骤**：

1. 读出该条目的**机制**（不是措辞），问『它防的是什么失效』
2. 找实体产品里的**对应物**：
   - 『焦点』→ 面板上被选中/高亮的控件
   - 『指针目标』→ 物理按键或触摸热区
   - 『程序可判定』→ 能被读屏/外部接口读出的语义
   - 『状态消息』→ 指示灯/提示音/振动
3. **优先查 EN 301 549 第 5/8 章有没有现成的硬件条款** —— 有就直接引条文，不要自己推
4. 若确无条文 → 在 ch01 各条的『向实体产品的迁移』里找本技能的推演，并**标注这是推演**

**判定**：迁移后的判据必须**可测量**（mm / N / dB / s / 对比度），
且能说出『依据是条文还是推演』。

**出处**：`ch01` 每条末的迁移段、`ch04` §4.2.2–4.2.3、`ch08` §8.5。

> **★ 顺序很重要**：先查硬件条文（强），再考虑推演（弱）。
> 例如『操作件要能被盲操作』不需要推演 —— EN 301 549 **5.5.2** 直接写了。

## P5 定触摸区尺寸与间距

**输入**：界面草图 + 目标级别（AA / AAA）

**步骤**：

1. 定**档位**：
   - **AA** → 目标 **24×24 CSS px**（WCAG 2.2 **2.5.8**）
   - **AAA** → 目标 **44×44 CSS px**（WCAG **2.5.5**，2.2 起改名 Enhanced）
2. 若坚持做小于 24 的控件 → 走 **spacing 例外**：
   以 **24 CSS px 直径**作圆，圆心置于每个目标包围盒中心，**圆与圆不得相交**
3. 换算到物理尺寸：按目标设备的 CSS px 定义（视觉角 ≈0.0213°）与视距推算
4. 检查例外是否成立（句内目标 / 等效控件 / UA 决定 / 本质必需）

**判定**：逐个控件测——要么本身 ≥24，要么**24px 圆不相交**。两者取其一即通过。

**出处**：`ch02` §2.2.5（2.5.8 含 spacing 原文）、`ch01` §1.2.15（2.5.5）。

> **★★ 落地提示：spacing 例外比『统一做大』实用得多。**
> 图标可以小，但相邻图标之间要留够 —— 这在小尺寸设备上更可行。

## P6 定固定式 ICT 的尺寸与高度

**输入**：自助机/信息亭/终端的外形与内部布局

**步骤**：

1. **先守强制线**（shall，必须满足）：
   - 每类操作件至少一件：距地 **≤1220 mm** 且 **≥380 mm**（8.3.2.1 / 8.3.2.2）
   - 至少一类显示屏：从操作区地面中心上方 **1015 mm** 处可读（8.3.5）
2. **再朝建议窗口靠**（recommended，非强制）：
   - 操作件 **800–1100 mm**
   - 显示屏 **1200–1400 mm**
3. 若操作件需 **>22.2 N** 才能操作 → 必须提供 **<22.2 N** 的替代方式（8.4.2.2）
4. 检查是否有**同时动作**要求 → 必须有替代（5.9）

**判定**：这四项任一不满足 = 不合规。
（1220/380/1015/22.2 N 是 shall；800–1100/1200–1400 是 recommended，只影响评分不影响合规。）

**出处**：`ch04` §4.2.3、`ch04` §4.3 判据表 #12–#17。

> **★★★★ 最容易出错的地方：把 800–1100 当强制、把 1220 当建议。恰好相反。**
> 复核：`grep -n "recommended that the possible height range" _standards/en_301549_v3.2.1.txt`

## P7 校验对比度三档用途

**输入**：一组配色（前景/背景）

**步骤**：

1. 算对比度：`(L1+0.05)/(L2+0.05)`，其中 `L = 0.2126R + 0.7152G + 0.0722B`（sRGB 线性化）
2. 按**用途**选门槛：

| 用途 | 门槛 | 依据 |
|---|---|---|
| 正文文字 | **4.5:1** | 1.4.3（AA） |
| 大字（≥18pt / ≥14pt bold） | **3:1** | 1.4.3 Large Text |
| 文字（增强） | **7:1**，大字 4.5:1 | 1.4.6（AAA） |
| 控件轮廓/状态/必需图形 | **3:1** | **1.4.11**（AA） |
| 焦点指示（同像素，聚焦前后） | **3:1** | **2.4.13**（AAA） |

3. 检查豁免：inactive 组件、纯装饰、纯 logo/品牌名文字

**判定**：**同一个 3:1 不能通用于所有用途** —— 文字用 3:1 只有在『大字』时才成立。

**出处**：`ch01` §1.2.5、§1.2.6；`ch02` §2.2.3；`glossary.md` §2（contrast ratio 与 relative luminance 的原文公式）。

> **★ 工业设计最该记的**：**1.4.11 给了『非文字』的 3:1**，
> 这是面板按键边界、指示灯状态、盖板与机身区分**唯一**的量化门槛。

## P8 写一份可复核的合规声明

**输入**：产品/页面清单 + 目标版本与级别

**步骤**：

1. **必含五项**（WCAG 5.3.1）：
   ① 声明日期 ② 指南名称+版本+URI ③ 所满足的级别 ④ 页面范围描述（含是否含子域）⑤ 所依赖的技术清单
2. **可选加分**（5.3.2）：超出所声称级别已满足的条目、所用辅助技术与浏览器、机器可读元数据
3. **范围要写清**（5.2.2/5.2.3）：含哪些布局变体、覆盖哪条完整流程
4. **AAA 条目单独列**，注明『超出 AA 的自愿满足项』，**不得作为整体声称**
5. 若有第三方内容或语言限制 → 用 **Statement of Partial Conformance** 的标准句式

**判定**：读者能否据此**复现你的测试范围**？不能 → 范围描述不合格。

**出处**：`ch03` §3.2.6–3.2.7。

> **★★ 判据：不发声明也完全合规（5.3.1 明说 claims are not required）。
> 但一旦发了，缺任一项就是不合格的声明 —— 比不发更糟。**

## P9 处理一份没抓到原文的标准

**输入**：一个你没有全文的标准（EN 17161 / ISO 21542 / GB/T 37668 正文 / 《无障碍环境建设法》）

**步骤**：

1. **先查有没有旁证**：别的已抓到的原文里是否引用它？
   - EN 301 549 **引用 ISO 21542（`[i.34]`，3 次）** → 可引题名与『被转述的建议值』
   - EN 301 549 **未引用 EN 17161（grep 0 次）** → 只能写『存在』
2. **把可写的与不可写的分开列**（照 `ch05` §5.1.2 / `ch06` §6.1.1 / `ch07` §7.2 的表）
3. **写进⑤本章空白**，注明『未获取 + 该去哪查』
4. **绝不**用二手网页转述补章节号

**判定**：写下每句话前问『这句能不能指到某个本地文件的具体位置？』
不能 → 删掉或移入空白清单。

**出处**：`ch05`（EN 17161）、`ch06`（ISO 21542）、`ch07`（中国）、`references/unavailable-standards.md`。

> **★★★ 判据：『存在』可以写，「内容」不可以。
> 连 ISO 21542 的题名能写，都是因为 EN 301 549 的文献表里逐字有它 —— 不是我记得。**
> 反例警告：`800–1100 mm` 是 EN 301 549 基于 ISO 图 53 的 **recommended**，
> **不能**说成『ISO 21542 规定 800–1100 mm』。

## P10 做一次按流程的验收

**输入**：一条完整用户任务（如『自助机购票：选择→确认→支付→取凭条』）

**步骤**：

1. **按流程切，不按页面切**（WCAG 5.2.3）：列出流程全部步骤
2. 对**每一步**跑条目清单（A/AA 全量），任一步不过 → 整条流程不过
3. 检查**每个布局变体**（5.2.2 Note 3）：横屏/竖屏、大字模式、不同断点**各自**验收
4. 检查**非干扰四条**（5.2.5）：1.4.2 / 2.1.2 / 2.3.1 / 2.2.2 —— 连第三方内容也要过
5. 实体部分跑 `ch08` §8.5 的 20 行清单
6. 记录**四种测试结果**：pass / fail / not applicable / not testable（EN §14）

**判定**：报告必须能回答四问 —— **哪一版 / 哪一级 / 哪个范围 / 哪些变体**。
缺一项＝不可复核。

**出处**：`ch03` §3.2.2–3.2.5、`ch04` §4.2.6、`ch08` §8.5。

> **★★★ 判据：验收清单要按流程串联，不是按屏罗列。**
> 常见失败：每屏单独看都过，但流程中间那一步的超时没提示 —— 整条流程不合规。

## 附：两个跨配方的自检动作

### A. 数字自检

任何写进文档的数字，跑一遍：

```bash
node _standards/verify_sc_coverage.js   # 条目/级别/阈值覆盖
node _standards/verify_quotes.js        # 引文逐字溯源
```

### B. 表述自检（六问）

1. 说了**哪一版**吗？（2.0 / 2.1 / 2.2 / EN 301 549 v3.2.1）
2. 说了**哪一级**吗？（A / AA / AAA）
3. 是 `shall` 还是 `should`？
4. 阈值是**强制**还是**建议**？
5. 这句能不能**指到本地文件**的具体位置？
6. 若不能 —— 它该不该进『本章空白』？
